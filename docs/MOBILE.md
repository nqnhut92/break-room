# Mobile UI and rendering

The entry form uses a two-column layout on landscape touch screens at least 600 CSS pixels wide. On portrait touch screens, the rotate prompt covers entry immediately, including first load, reload, auto-rejoin and disconnected states. `viewport.js` owns this gate before the game/WebGL module initializes; it does not depend on `S.joined`. Landscape reveals the entry form. The DOM is never rotated. Native browser fullscreen/orientation APIs are optional.

The header shows room, online count, sound and rage. Health stays above the local character. Camera zoom buttons sit below settings. The first camera distance is 900 on phones and 1450 on touch tablets (short side at least 600px, every iPad); computers start at 1300. The range is 560–2300, and a player's own zoom is remembered. Chat and the emoji toggle sit at the bottom center. The skill icon sits to the left of attack, matching its 90×58px touch target with a 24px gap. The emoji toggle opens a single row above the bottom controls. Choices close after selection or an outside tap. A full rage bar reveals ULTI above the attack button; after rage is spent, it hides again.

## Viewport and gestures

`public/viewport.js` measures the shared CSS layout surface `#app` for canvas dimensions and HUD sizing. The app uses `100dvh` with a minimum from layout `window.innerHeight`, plus the existing percentage fallback; both subtract the reserved system band, so a stale root/dynamic-height value after rotation cannot leave the app shorter than the layout viewport. On coarse-pointer screens, the reserved top band is the supplied top safe-area inset plus up to 16px extra clearance (`safeTop + min(safeTop, 16px)`). It is zero when the supplied inset is zero. The world and HUD both start below this dark band, with the remaining height used for camera/renderer sizing. The app-local top inset is zero to avoid double padding. Layout containment gives the canvas and fixed HUD the same containing block. Picking subtracts the canvas client rectangle; notices/maps subtract the app origin, while joystick client coordinates stay paired with client rectangles. Keyboard inset calculations include the app origin. ResizeObserver, native orientation/fullscreen events and brief deferred rechecks handle late layout changes. A Home Screen launch can report a short layout height at first paint and send no resize afterwards (only rotating the phone corrected it), so the page also re-measures on `load` and at 0.3 s, 1 s and 2.5 s after start; `test/viewport.js` covers this with a stale first measurement. This is not yet confirmed on a physical iPhone. Do not derive game dimensions from `visualViewport.width/height`: page zoom shrinks those measurements. Visual viewport events update only the keyboard inset for chat, without reallocating the renderer or resetting controls.

The game canvas, joystick and attack button use `touch-action: none`, cancel native `touchstart`, and cancel double-click default handling. The game handles two-finger camera zoom itself. Dialogs retain vertical scrolling. In help, only `#helpContent` owns scrolling: an unscrollable nested list with `overscroll-behavior: contain` would otherwise swallow swipes before they reach the outer scroller. Mobile text sizing is fixed at 100% so rotation does not trigger automatic text enlargement.

## Impact performance

Impact effects previously initialized some WebGL programs on their first visible use. A local Chromium CPU profile of the first held hammer attack included a synchronous `getProgramInfoLog` wait. Effects now use asynchronous shader preparation plus one transparent draw to initialize first-use uniforms and textures. The transparent warmup uses the normal renderer directly; it adds no compositor, post-processing or framebuffer chain. Preparation is repeated when graphics quality changes.

Debris previously submitted all 520 instance slots on every frame, including zero-scale inactive slots, in both the color and shadow passes. It now packs only living fragments into the draw range, uploads only that part of the matrix/color buffers, and skips tiny fragment shadows on touch devices. Empty scenes submit zero debris instances. Mobile camera shake uses a smaller continuous oscillation instead of independent random offsets on every display frame. This changes impact feedback, not combat timing or damage.

Local verification found zero new program initializations during the measured first hammer attack after warmup, and zero idle debris instances (previously 520 per pass). These are pipeline checks, not an iPhone FPS benchmark: software WebGL in headless Edge is not representative of an iPhone GPU. High/low settings still share scene geometry and much of the effect/CPU work, so a graphics toggle alone cannot eliminate every first-use hitch.

## Joystick recovery

Joystick ownership is a pointer id plus pointer type. Move/up/cancel are observed at window capture phase so a terminal event delivered outside the pad still clears movement. Native touchend/touchcancel provide a fallback when no touch originating on the pad remains, even if an attack finger is still down. A new primary touch can replace stale ownership; a secondary finger cannot steal a valid capture. Before movement, a pointer that no longer owns capture is returned to neutral. Capture/release failures also clear state, and a delayed lost-capture event is ignored if capture is currently active.

There is no inactivity timeout on a stationary held thumb. Chat focus, window blur, rotation and visibility changes retain their existing reset paths. The iPhone report (a direction sometimes sticks until opening/closing chat) suggests stale input state but does not establish which native event Safari lost.

Run `npm run test:joystick` with Chromium installed (or set `CHROMIUM_PATH`). The test uses native Chromium touch input, real game/UI/socket logic, and a stub renderer. It exercises direction changes, stationary holds, simultaneous attack, terminal events outside the pad, missing pointer-end fallbacks, delayed capture loss, capture/release exceptions, stale ids and chat recovery. Missing-event cases are fault injection, not a reproduction of the exact iPhone failure.

On the actual iPhone, test repeated drags/lifts including off-pad release, joystick plus attack, opening/closing chat, app switching and native rotation. Releasing and touching the pad again should recover without opening chat; a continuously held thumb should not stop just because it stays still.

## Safe areas and rotation previews

The world background fills the app surface. Important content uses the browser-provided `safe-area-inset-*` values plus normal margins: header, map/chat, joystick, attack/skill/chat/emoji controls, notices, keyboard chat and dialog contents. The centered groups shift to the center of the usable width when left/right insets differ. No iPhone model detection or fixed notch width is used in production; Android cutouts and gesture/side-navigation bars use the same CSS variables. On short landscape surfaces, the map shrinks to stay above the joystick. Server shocks now use pooled electric arcs/sparks and normal HP-loss numbers, without a floating “GIẬT ĐIỆN” label or introductory toast.

This follows [WebKit's edge-to-edge and safe-area guidance](https://webkit.org/blog/7929/designing-websites-for-iphone-x/) and [Chrome Android's edge-to-edge guidance](https://developer.chrome.com/docs/css-ui/edge-to-edge). Side/bottom backgrounds still extend behind their safe areas. The reserved top band is an explicit layout choice to keep gameplay clear of system blur; resize the renderer/camera to the remaining surface rather than merely translating an unchanged canvas. Do not disable pinch accessibility globally.

The Home Screen app no longer sets `apple-mobile-web-app-status-bar-style`. The clock/battery row remains visible; the system chooses its appearance. This follows Apple's [current WebKit guidance](https://bugs.webkit.org/show_bug.cgi?id=317153#c2) to remove deprecated `black-translucent`. The earlier explicit top-band layout remains as a fallback whenever the browser supplies a nonzero top inset; when the system already places the page below the status bar and supplies zero top inset, no extra band is added. Changing this meta configuration may require removing the old Home Screen icon and adding the site again: [WebKit report 316008](https://bugs.webkit.org/show_bug.cgi?id=316008) records install-time status-bar behavior. Ordinary reloads may retain the installed shell's old configuration.

A physical iPad Home Screen launch, after removing `black-translucent` and re-adding the icon, still showed a washed/blurred strip at the top. iPadOS draws a scroll-edge blur in the status bar and samples it from the top of the page, so the game showed through it. A reading on an iPad Pro 11-inch (M4, iPadOS 26) settled the geometry: `screen 834x1210`, `innerHeight` 802, `100dvh`/`100svh` 802, `100lvh` 834, safe-area top/bottom 0/25. The web view already starts below the 32pt status bar, and its layout viewport is correct. `100lvh` still counts the bar (compare [WebKit report 316008](https://bugs.webkit.org/show_bug.cgi?id=316008)). A first attempt treated `100lvh − innerHeight` as a missing top inset. It reserved the bar a second time (a 64pt dark band) and pushed the bottom controls 32pt below the screen. Do not size or offset the game from `100lvh`, `screen` or their difference. The bar's height also differs between iPad models, so do not hard-code it either.

The fix keeps layout-viewport sizing and adds `#statusBand`: a fixed, full-width, 12px element at the top with `background: var(--bg)` clipped to text, so it paints nothing and takes no input. The approach follows [coder/xum](https://github.com/coder/xum/pull/5656)'s iPad follow-up: WebKit tints the iPad scroll-edge effect from a fixed top element at least 90% wide and taller than 10px, so the status bar shows the page colour instead of blurred game. This tint rule comes from that third-party report, not from WebKit documentation; confirm it on the device. Settings (touch screens) ends with one line of raw measurements: screen, inner size, root client height, `100dvh`/`100lvh`/`100svh`, safe-area top/bottom, the `#app` top+height and standalone mode. Ask for that line before changing this layout again. Keep sizing from the layout/app surface, not `screen.height` or `visualViewport`: inflating a genuinely shorter viewport would hide bottom controls. Extra top clearance has precedent in [OpenCode's merged phone fix](https://github.com/anomalyco/opencode/pull/53297), but its measurements do not establish iPad blur dimensions.

`npm run test:mobile-safe-area` also covers a 1210×834 iPad Pro 11-inch landscape layout with injected top/bottom insets (24/20px and 36/20px). It checks header, map/chat, controls and settings bounds, plus canvas coverage from the reserved band to the bottom of the layout viewport and matching renderer dimensions. A short-launch case starts CSS/layout height 24px short, restores `innerHeight` without a resize event, and checks that startup remeasurement fills the canvas. An additional external-status-bar profile supplies a 1210×810 content viewport inside a 1210×834 screen with an oversized legacy root; it checks no double top reservation, matching app/canvas/renderer height and accessible bottom controls. An iPad Home Screen profile replays the measured geometry above (iPad user agent, `navigator.standalone`, 1210×802 layout viewport, portrait-reported 834×1210 screen, 834px page height). It checks that the canvas fills 0–802 with no second band, that the tint band is full width, 12px tall, text-clipped and click-through, that the HUD stays above the 25px home indicator, and the Settings readout. These supplied values exercise the layout contract, not measured iPadOS Liquid Glass geometry; physical iPad verification remains necessary.

Run `npm run test:mobile-safe-area` with Chromium/`CHROMIUM_PATH` for injected insets representing left/right cutouts, bottom gestures, side navigation, no cutout and a short landscape display. It also fault-injects stale root/app heights and checks native rotation/viewport growth. `npm run test:office-ui` uses real WebGL for desktop, plain mobile and simulated iPhone-left/iPhone-right/Android previews; hardware-shaped masks are test-only visual aids. These checks establish layout behavior under supplied insets, not the exact Dynamic Island dimensions or a reproduction on physical Safari/Android hardware. Repeat rotation both ways, browser toolbar changes, keyboard open/close and Home Screen launch on devices before claiming the reported iPhone gap fully resolved.


## Mobile chat layout

On landscape touch screens, skill is a 90×58px icon button with a 34px icon, matching attack. It sits to the left of attack with a 24px gap. Drink/ULTI stay above attack; skill does not move when those appear. Chat history/preview, compose and emoji share the bottom dock. The dock centers within the available gap from 16px after the joystick to 16px before skill; its width is capped at 480px. Its placement is recomputed from actual control rectangles after layout/resize, so it stays clear of both thumbs. The preview is always visible while joined, including before the first message; it shows the latest line, or a prompt when empty. A new message expands history upward to 104px (four 20px text lines plus gaps/padding). After eight seconds idle, history collapses back to the 48px preview. The dock bottom and all button tap targets stay fixed. Tapping the preview opens history (or compose when empty); the compose button opens the input. Holding/scrolling history and editing keep it expanded. Long messages wrap inside the full history; only the compact preview is truncated. Older messages remain in the same native scrollable log. Desktop retains its persistent chat panel.

`npm run test:mobile-chat` checks expanded/idle states, reading older history, stable tap targets, a long message sent through the actual form/server, wrapping and 956×440/844×390/740×320 layouts. `CHAT_REAL_RENDERER=1` uses actual WebGL and saves a local screenshot in `work/`; supplied history is test data. `npm run test:renderer` also checks picking after a canvas origin shift. ## Local map and full-room overview

The mini map is a circular radar centered on the player, magnifying a fixed 1,500-unit radius. The full-office overview labels each room (names and bounds sent in the welcome as `rooms`) plus the LOBBY. The inner 78% stays clear; fading is concentrated near the rim. Camera zoom does not change its scale or shrink the full office into its center. Boss/mini-boss markers outside the circle are omitted. Tap the mini map to open the full-room overview. Tap anywhere else, the mini map again or the 44px close target to close it. Taps on the joystick and the attack, skill, ULTI and drink buttons keep it open, so players can keep moving and fighting. No permanent extra HUD button is added. The existing map utility and desktop M still hide/show the mini map. Desktop players can hold Tab for the overview and release to close; click-to-open remains available, with Esc/× to close. Blur clears the held overview, and typing chat retains normal keyboard behavior.

The overview does not pause simulation or clear held movement. Its backdrop/canvas do not capture joystick or attack input; only the close button takes pointer input. The overview canvas fits within the landscape screen and uses the existing safe content layout around controls. Boss mottos appear immediately below names on desktop and on coarse-pointer landscape viewports at least 1000px wide and 600px tall. Every iPad qualifies, including iPad mini (1133×744, and shorter with Safari's toolbar or a Home Screen status bar); landscape phones (at most about 956×440) do not. Mottos of bosses standing close together may overlap; that was accepted. They show/hide automatically on resize without rebuilding rigs. This threshold measures usable layout space rather than claiming physical-inch/model detection; split-screen or browser chrome can make a large tablet use the compact layout. `npm run test:minimap` covers touch and desktop input/layout; also verify real phones for readability while running and turning.
