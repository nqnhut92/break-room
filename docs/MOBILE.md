# Mobile UI and rendering

The entry form uses a two-column layout on landscape touch screens at least 600 CSS pixels wide. On portrait touch screens, the rotate prompt covers entry immediately, including first load, reload, auto-rejoin and disconnected states. `viewport.js` owns this gate before the game/WebGL module initializes; it does not depend on `S.joined`. Landscape reveals the entry form. The DOM is never rotated. Native browser fullscreen/orientation APIs are optional.

The header shows room, online count, sound and rage. Health stays above the local character. Camera zoom buttons sit below settings. The starting camera view is also the closest one, so + is dimmed until the player zooms out with −. Its distance scales with the game height in CSS pixels: `1.25 × (380 + 1.335 × height)`, clamped to 800–2600. That is about 1125 on a 390px phone, 1815 on an 802px iPad and 2060 on a 950px desktop window; players on an iPhone and an iPad each settled one step further out than the unscaled fit. The furthest view is at least 2300 and 1.6× the start, capped at 3600. The +/− buttons move through four evenly spaced (equal-ratio) levels between them, so every press changes the view by the same proportion; pinch and the mouse wheel stay continuous. Until the player zooms, window size changes move the start view with it; a chosen zoom is remembered and kept within the current range. Chat and the emoji toggle sit at the bottom center. The skill icon sits to the left of attack, matching its 90×58px touch target with a 24px gap. The emoji toggle opens a single row above the bottom controls. Choices close after selection or an outside tap. A full rage bar reveals ULTI above the attack button; after rage is spent, it hides again.

## Viewport and gestures

`public/viewport.js` measures the shared CSS layout surface `#app` for canvas dimensions and HUD sizing. The app uses `100dvh` with a minimum from layout `window.innerHeight`, plus the existing percentage fallback; both subtract the reserved system band, so a stale root/dynamic-height value after rotation cannot leave the app shorter than the layout viewport. On coarse-pointer screens, the reserved top band is the supplied top safe-area inset plus up to 16px extra clearance (`safeTop + min(safeTop, 16px)`). It is zero when the supplied inset is zero. The world and HUD both start below this dark band, with the remaining height used for camera/renderer sizing. The app-local top inset is zero to avoid double padding. Layout containment gives the canvas and fixed HUD the same containing block. Picking subtracts the canvas client rectangle; notices/maps subtract the app origin, while joystick client coordinates stay paired with client rectangles. Keyboard inset calculations include the app origin. ResizeObserver, native orientation/fullscreen events and brief deferred rechecks handle late layout changes. A Home Screen launch can report a short layout height at first paint and send no resize afterwards (only rotating the phone corrected it), so the page also re-measures on `load` and at 0.3 s, 1 s and 2.5 s after start; `test/viewport.js` covers this with a stale first measurement. Physical iPhone verification found the final layout correct, with a brief startup shift still reported. Do not derive game dimensions from `visualViewport.width/height`: page zoom shrinks those measurements. Visual viewport events update only the keyboard inset for chat, without reallocating the renderer or resetting controls.

On iPhone/iPod Home Screen apps in landscape, the reserved top band is zero because there is no landscape status bar. `viewport.js` marks only that device/display combination; side and bottom safe areas, portrait top clearance, and iPad status-bar handling remain in place. `test:mobile-safe-area` injects a stale 100px portrait top inset before a cold landscape load: previously it displaced the app by 116px and reduced a 390px play surface to 274px. The regression now checks full landscape height and rotation back to portrait. This is a fault-injection reproduction of a possible cause, not confirmation of the native iPhone launch bug; verify a fully terminated Home Screen app launched in both landscape directions on hardware.

iPhone Home Screen apps use an absolutely positioned `#app` instead of a fixed outer wrapper. Layout containment still anchors the fixed HUD to that wrapper. This is a targeted workaround candidate for the standalone fixed-element viewport displacement described in [WebKit 322083](https://bugs.webkit.org/show_bug.cgi?id=322083); it does not use visual-viewport dimensions or forced scroll/zoom. This wrapper change alone did not resolve the native launch issue; status-bar configuration and app-sized form queries are also required. Desktop browser tests verify sizing and layout compatibility rather than reproduce the native lock/sleep state. iPad, Android and regular browser tabs retain the fixed wrapper.

The game canvas, joystick and attack button use `touch-action: none`, cancel native `touchstart`, and cancel double-click default handling. The game handles two-finger camera zoom itself. The page itself never zooms, as a product requirement: every element defaults to `touch-action: manipulation` (no double-tap zoom; a double tap on the leaderboard used to zoom Safari), the viewport meta sets `maximum-scale=1,user-scalable=no` (Android pinch and iOS input focus zoom), and `viewport.js` cancels iOS `gesturestart/gesturechange/gestureend` and `dblclick` defaults (iOS ignores `user-scalable=no`). `npm run test:mobile-safe-area` checks the meta, the computed touch actions and the cancelled events; confirm double tap and pinch on HUD panels on a real iPhone/iPad. Dialogs retain vertical scrolling (`manipulation` still allows panning). In help, only `#helpContent` owns scrolling: an unscrollable nested list with `overscroll-behavior: contain` would otherwise swallow swipes before they reach the outer scroller. Mobile text sizing is fixed at 100% so rotation does not trigger automatic text enlargement.

## Impact performance

Impact effects previously initialized some WebGL programs on their first visible use. A local Chromium CPU profile of the first held hammer attack included a synchronous `getProgramInfoLog` wait. Effects now use asynchronous shader preparation plus one transparent draw to initialize first-use uniforms and textures. The transparent warmup uses the normal renderer directly; it adds no compositor, post-processing or framebuffer chain. Preparation is repeated when graphics quality changes.

Debris previously submitted all 520 instance slots on every frame, including zero-scale inactive slots, in both the color and shadow passes. It now packs only living fragments into the draw range, uploads only that part of the matrix/color buffers, and skips tiny fragment shadows on touch devices. Empty scenes submit zero debris instances. Mobile camera shake uses a smaller continuous oscillation instead of independent random offsets on every display frame. This changes impact feedback, not combat timing or damage.

Local verification found zero new program initializations during the measured first hammer attack after warmup, and zero idle debris instances (previously 520 per pass). These are pipeline checks, not an iPhone FPS benchmark: software WebGL in headless Edge is not representative of an iPhone GPU. High/low settings still share scene geometry and much of the effect/CPU work, so a graphics toggle alone cannot eliminate every first-use hitch.

## Joystick recovery

The pad is 27% of the game height, clamped to 104–176px: landscape phones stay at about 104–110px, an 11-inch iPad reaches the 176px cap (the old 136px cap looked small there). The knob reaches full speed at 30% of the pad width, so the thumb travel grows with the pad (about 53px at 176px). Confirm the larger pad on a physical iPad.

Joystick ownership is a pointer id plus pointer type. Move/up/cancel are observed at window capture phase so a terminal event delivered outside the pad still clears movement. Native touchend/touchcancel provide a fallback when no touch originating on the pad remains, even if an attack finger is still down. A new primary touch can replace stale ownership; a secondary finger cannot steal a valid capture. Before movement, a pointer that no longer owns capture is returned to neutral. Capture/release failures also clear state, and a delayed lost-capture event is ignored if capture is currently active.

There is no inactivity timeout on a stationary held thumb. Chat focus, window blur, rotation and visibility changes retain their existing reset paths. The iPhone report (a direction sometimes sticks until opening/closing chat) suggests stale input state but does not establish which native event Safari lost.

Run `npm run test:joystick` with Chromium installed (or set `CHROMIUM_PATH`). The test uses native Chromium touch input, real game/UI/socket logic, and a stub renderer. It exercises direction changes, stationary holds, simultaneous attack, terminal events outside the pad, missing pointer-end fallbacks, delayed capture loss, capture/release exceptions, stale ids and chat recovery. Missing-event cases are fault injection, not a reproduction of the exact iPhone failure.

On the actual iPhone, test repeated drags/lifts including off-pad release, joystick plus attack, opening/closing chat, app switching and native rotation. Releasing and touching the pad again should recover without opening chat; a continuously held thumb should not stop just because it stays still.

### Buttons while moving

iOS WebKit (Safari, and Edge or Chrome on iOS) synthesizes no `click` for a tap while another finger is down, so with the joystick held only SMASH worked: it acts on `pointerdown`. ### Home Screen gate

Phones and tablets play from the Home Screen app only (product requirement, November 2026; [ADR 0011](adr/0011-home-screen-gate.md)). A touch device (`pointer: coarse`, or iOS/iPadOS) that opens the game in a browser tab (neither iOS `navigator.standalone` nor an app display mode is active) gets `#installOverlay`: a full-screen prompt like the rotate prompt (game icon, title, numbered steps), drawn above the rotate prompt because adding the icon works in portrait too. The join form underneath is hidden. Nothing joins from the tab: the submit handler refuses, and so does the reload auto-join. An inline script in `index.html` sets `html.install-gate` before the first paint, which shows the prompt with the Safari steps at once; `game.js` has the final say and fills in the steps for the browser. On short landscape phones (height up to 500px) the card widens so nothing scrolls. Desktops are not gated. Automated browsers (`navigator.webdriver`, i.e. Playwright) are exempt so the touch test suites can still join.

The shared `HomeScreenApp` check in the page head is used both before first paint and by `game.js`. It accepts iOS `navigator.standalone` or `display-mode` standalone, fullscreen, minimal-ui or window-controls-overlay. The gate is rechecked when any of those modes changes, on `pageshow`, and when the page becomes visible. Accepting an install dialog or firing `appinstalled` only changes the browser-tab instructions; it never grants entry to that tab. No local-storage install flag or URL parameter bypasses the gate.

Web pages cannot tell whether the icon already exists, only whether this launch came from it, so the last step is always "Mở game từ icon mới". Earlier versions showed a dismissible card, first in the office and then on the join screen. On iPhone/iPad, office notices from Prof. K and the patrol could cancel the in-office card. A blocking prompt like the rotate prompt makes the Home Screen requirement visible before joining.

- Android/Chromium: without `beforeinstallprompt` the card gives the menu steps (⋮ → Thêm vào màn hình chính / Cài đặt ứng dụng). With the event it adds a **Cài app** button that calls `prompt()`, the browser's own install dialog; after the player accepts, the card says to open the game from the icon. `manifest.json` (`display: standalone`) lists 192px and 512px PNG icons. There is no service worker. Physical Android Chrome feedback confirms the install button/dialog appears, but an icon launch without browser bars was reported to show the install prompt again. Expanded display-mode and lifecycle checks cover potential false negatives; the precise native display mode and the fix still need confirmation on that device.
- iOS/iPadOS: no browser exposes an install API (all use WebKit), so the card shows steps only. iPadOS reporting a Mac user agent is recognised by `maxTouchPoints > 1`; an iPad with a trackpad reports a fine pointer, so iOS is gated without the coarse-pointer check.
  - iPhone: Safari "Chia sẻ → Thêm vào Màn hình chính"; Edge/Chrome/Firefox "⋯ → Chia sẻ → Thêm vào Màn hình chính". Device observation (November 2026, physical iPhone): Edge on iPhone offers Add to Home Screen, and the icon it adds opens like Safari's (without browser bars).

If a browser in desktop mode hides its name from the user agent, it gets the Safari steps.

Device checks still needed: that a Home Screen launch from Safari and from Edge on iPhone reports standalone (otherwise players are locked out), that Android Chrome's installed app does, and Google login inside the Home Screen app (iOS keeps its storage apart from Safari, so a sign-in made in Safari does not carry over, and the OAuth return must land back in the app).

## Safe areas and rotation previews

The world background fills the app surface. Important content uses the browser-provided `safe-area-inset-*` values plus normal margins: header, map/chat, joystick, attack/skill/chat/emoji controls, notices, keyboard chat and dialog contents. The centered groups shift to the center of the usable width when left/right insets differ. No iPhone model detection or fixed notch width is used in production; Android cutouts and gesture/side-navigation bars use the same CSS variables. On short landscape surfaces, the map shrinks to stay above the joystick. Server shocks now use pooled electric arcs/sparks and normal HP-loss numbers, without a floating “GIẬT ĐIỆN” label or introductory toast.

This follows [WebKit's edge-to-edge and safe-area guidance](https://webkit.org/blog/7929/designing-websites-for-iphone-x/) and [Chrome Android's edge-to-edge guidance](https://developer.chrome.com/docs/css-ui/edge-to-edge). Side/bottom backgrounds still extend behind their safe areas. The reserved top band is an explicit layout choice to keep gameplay clear of system blur; resize the renderer/camera to the remaining surface rather than merely translating an unchanged canvas.

iPad, Android and desktop do not set `apple-mobile-web-app-status-bar-style`; the system chooses status-bar appearance. This follows Apple's [WebKit guidance](https://bugs.webkit.org/show_bug.cgi?id=317153#c2) to remove deprecated `black-translucent`. iPhone/iPod have a narrow exception: an early head script adds `black-translucent` on both the Safari install page and standalone launches. [Apple's archived meta reference](https://developer.apple.com/library/archive/documentation/AppleApplications/Reference/SafariHTMLRef/Articles/MetaTags.html) describes its edge-to-edge content behavior, as opposed to placing web content below the status bar. This is an install-time workaround candidate for the measured lock/sleep landscape gap, not a general recommendation to use deprecated metadata. The earlier explicit top-band layout remains a fallback for nonzero top safe insets; landscape iPhone standalone mode reserves none. The existing iPad geometry and status-bar tint treatment are preserved.
